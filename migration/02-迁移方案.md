# 02 迁移方案

本文档定义目标架构与技术方案。最终决策见 [README.md](README.md) 决策记录；
现状依据见 [01-现状分析.md](01-现状分析.md)。

## 1. 总体思路

迁移本质是三件事，工作量差异极大：

| 部分 | 迁移方式 | 工作量 |
|---|---|---|
| Go `internal/` 后端逻辑（~1,460 行） | **逐行移植**为 C# 服务类，逻辑 1:1（含所有字节级 hack） | 小 |
| `app.go` 绑定层 + 前端 IPC 兼容层 | **整个消失**——同进程，ViewModel 直接 `await` 服务，事件用 C# event / `IProgress<T>` | 净删除 |
| React 前端（8,000 行 TSX + 2,000 CSS） | **完全重写**为 WPF（XAML + MVVM） | **大（占总量 70%+）** |

Wails 的批量 API 当初是为减少 IPC 往返设计的；C# 同进程直接循环 + `Parallel.ForEachAsync` 即可，分批壳不再需要（并行度保留：文本 8 / 图像 4 / zipmod 4）。

## 3. 技术映射（Go → C#）

| Go | C# |
|---|---|
| `net/http` + proxy + Range | `HttpClient` + `HttpClientHandler.Proxy`（含 `NetworkCredential` 认证）+ `RangeHeaderValue` |
| `archive/zip` | `System.IO.Compression.ZipArchive` |
| `compress/flate`（裸 DEFLATE） | `System.IO.Compression.DeflateStream`（**不能用 ZLibStream**） |
| `encoding/xml` | `System.Xml.Serialization` / `XDocument` |
| goquery（`table#indexlist tr` 选择器） | **HtmlAgilityPack** |
| `go:embed sideload.zip` | csproj `<EmbeddedResource>` + `Assembly.GetManifestResourceStream` |
| goroutine + WaitGroup + Mutex + 信号量 | `async/await` + `Task.WhenAll` + `SemaphoreSlim` + `Parallel.ForEachAsync` |
| `context.Context` 取消 | `CancellationTokenSource` |
| Wails EventsEmit/EventsOn | C# `event` / `IProgress<T>`（async 续体经 SynchronizationContext 自动回 UI 线程） |
| IndexedDB / localStorage / Go 配置 JSON（三处分散） | **统一一份** `%AppData%/hs2-tools/settings.json`（强类型 `AppSettings`），收藏、扫描缓存一并纳入 |
| F15 按键防休眠 hack | P/Invoke `SetThreadExecutionState(ES_CONTINUOUS \| ES_SYSTEM_REQUIRED)`，恢复用 `ES_CONTINUOUS` |
| `exec.Command`（启动游戏、explorer /select,） | `Process.Start`（`WorkingDirectory` 设为游戏目录） |
| React + Zustand | WPF XAML + `CommunityToolkit.Mvvm`（`ObservableObject`/`RelayCommand`） |

## 4. 多窗体架构

**原则：状态全部下沉到服务层单例，Window 只是视图。**

- **服务容器**：`App.xaml.cs` 启动时创建全部服务单例（ConfigService、ScanCacheService、DownloadManager、SideloaderService、GameLauncherService），以静态容器或构造注入提供。
- **WindowManager**：每个页面 Window 只创建一次；导航 = `Show()` + `Activate()`；用户点关闭 = 取消 Closing + `Hide()`——**保持状态**（滚动位置、筛选条件、已加载缩略图全部保留）。MainWindow 真正关闭时才 `Application.Current.Shutdown()`。
- **跨窗体通信 = 服务层事件**，窗口之间不直接引用：
  - 配置改动 → `ConfigService.Changed` 事件 → 各已打开窗口的 ViewModel 自行刷新；
  - 下载进度/完成 → `DownloadManager` 事件 → DownloadWindow 和 CharaWindow 的下载按钮各自订阅；
  - 爬虫进度/完成 → `SideloaderService` 事件。
- **订阅纪律**：ViewModel 在窗口 `Loaded`/`IsVisibleChanged` 时订阅，Hide 时退订，重开再订阅——防止重复订阅与泄漏。下载任务在 DownloadManager 中持续运行，**关闭 DownloadWindow 不中断下载**，重开时从任务表重建视图。

**关键控件——CardGridControl（卡片网格）**：

- `ItemsControl` + 虚拟化面板；WPF **无内置 VirtualizingWrapPanel**，需自带一个简单实现（约 200 行，0.5~1 天）或按行分组虚拟化。
- 数据流与原前端一致：全量路径 → 过滤/排序 → 可视区分批解析（C# 版**一次读盘**同时拿名称+缩略图，修掉原版读两遍的问题），缩略图 `BitmapImage` 做 LRU 缓存控内存。
- 收藏存统一配置文件；排序用 `StringComparer.Create(new CultureInfo("zh-CN"), …)` 对齐原版中文排序行为。

**主题（A7）**：单主题。`ResourceDictionary` 集中定义颜色/画刷资源，后期加第二主题时换字典即可，控件一律用 `DynamicResource` 引用，不留硬编码色值。

## 6. 异步与线程模型

- 所有 IO/网络/解析走 `async/await`；CPU 密集的批量解析用 `Parallel.ForEachAsync`（并发度：文本 8 / 图像 4 / zipmod 4 / 爬虫 mod 10、目录 3，照搬原版）。
- 进度上报 `IProgress<T>` 或服务事件（内部注意封送到 UI 线程：`IProgress` 天然安全；自建 event 由订阅方用 Dispatcher 处理）。
- 取消一律 `CancellationTokenSource`：DownloaderService 的活动任务表（对应原 `activeDownloads` map）、SideloaderService 单实例运行锁（对应 `sideloaderMu`）。
- 长任务（扫描、爬虫、整理）全部后台执行，UI 只订阅进度。

## 9. 移植注意点（实现期对照）

逐条对应 [01-现状分析.md](01-现状分析.md) 第 7 节的复刻清单。额外提醒：

- Go `string(bytes)` 对无效 UTF-8 保留原始字节，.NET `Encoding.UTF8.GetString` 默认替换为 U+FFFD——乱码卡名输出可能不同，测试期用真实卡片对比确认可接受。
- 所有原版"静默吞错"点位（批量解析失败跳过、爬虫单页失败直接返回）迁移时**至少记日志**，不要默默 continue。
- `SideloaderService.Run` 设计为可重入（每次运行新建内部状态），修掉原版非可重入的坑。

## 10. 实施期修订记录（阶段 1 实测发现，2026-07）

阶段 1 移植过程中发现并处理的 .NET 平台差异与对原方案的偏离。后续阶段实现网络/IO 功能前先读本节。

### 10.1 .NET HttpClient 的三个平台陷阱（已修复，均有测试）

| 陷阱 | 现象 | 对策（已落实） |
|---|---|---|
| **默认走系统代理** | `HttpClientHandler` 未设 Proxy 时使用系统代理（Go 自建 Transport 未配代理时直连），导致爬虫绕路代理、行为与 Go 不一致 | 未配置代理时显式 `handler.UseProxy = false`（SideloaderService / DownloaderService） |
| **HTTP/2 设置无效** | `HttpClient.DefaultRequestVersion = 2.0` **不生效**（请求消息 `Version` 默认 1.1 覆盖客户端默认）；目标站点（Apache）对 h1 回 `Connection: close`，每请求新建 TCP+TLS → 速度仅 Go 的 1/3、连接 churn 致进程崩溃 | 在**每个** `HttpRequestMessage` 上设 `Version = 2.0, VersionPolicy = RequestVersionOrLower`（修复后 300+ mod/分钟、连接数 2 条、内存 <40MB，与 Go 相当） |
| **Range 被 200 应答** | 代理干预时 Range 请求可能收到 200 全量响应；若按 Go 原样 `ReadAll` 并前插累积，16 次 × 全文件 × 10 并发 → 数 GB 内存 | 200 且非整文件请求的块**丢弃**（Range 正常站点恒为 206，此分支仅代理干预时触发）；≤64KB 小文件整取后本地头/manifest **内存切片**不再发请求 |

### 10.2 安全防御（真实站点未触发，纯兜底）

- `SideloaderService`：manifest 压缩大小 > 4MB 视为解析异常，跳过并记日志。
- `ZipRemoteReader.ExtractManifestGuid`：DEFLATE 解压上限 16MB，防解压炸弹。

### 10.3 与 Go 版的行为差异说明（非缺陷，已确认）

- **下载"服务器不支持续传，重新开始"提示**：Go 源码该分支不可达（200 时 `startPos` 已先重置为 0），C# 版同样保留为不可达代码；实际整文件重写行为一致。
- **爬虫重复 guid 的相对路径**：站点上同一 guid 存在于多个目录（如 Exclusive HS2/AIS），结果 dict"后写覆盖"；Go 版因 map 随机序选路本身就是随机的，C# 版可能选出不同目录——对照验证按重合度 + 差异占比（≤1%）判定，不要求路径逐一致。
- **DownloadManager 同名任务**：原版直接覆盖 `activeDownloads` 条目（旧任务失控），C# 版拒绝重复触发（返回 false）。
- **测试基础设施**：读取 Go CLI 进程输出须显式 `StandardOutputEncoding = UTF8`（默认 ANSI/GBK 码页会破坏 JSON）；Go sideloader CLI 需要 go ≥ 1.25 工具链（本机 1.24 + 自动下载 1.25.12 可用）。
- 阶段 0 决策：测试夹具不收集真实卡片/zipmod 大文件，改为**程序化合成夹具**（PNG 标记字节、Store/Deflate/脏 manifest zipmod、多 dummy 条目大 zipmod、autoindex HTML），可重复且无仓库膨胀；真实 sideload.zip 照常内嵌。
